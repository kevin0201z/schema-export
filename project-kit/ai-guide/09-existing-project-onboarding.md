# 已有项目接入流程

> AI 快速摘要
>
> - 适用场景：把本指南接入已经存在的项目。
> - 必须产出：项目现状分析、缺失文档列表、接入建议。
> - 硬性阻断：用户确认前，不要修改代码或补写会改变现状含义的文档。
> - 相关模板：`requirements.template.md`、`architecture.template.md`、`tasks.template.md`
> - 可跳过场景：新项目初始化、单个功能开发。

本文档用于指导 AI 将本指南接入已经存在的项目。

目标是在不破坏现有代码的前提下，识别项目现状、补齐关键文档、建立后续开发规则。

## 1. 接入原则

1. 先扫描，不修改。
2. 先理解现状，再补文档。
3. 不重构已有代码，除非用户明确要求。
4. 不擅自改变技术栈。
5. 不删除或覆盖已有文件。
6. 文档应反映当前真实代码，而不是理想设计。

## 2. 接入流程

AI 必须按以下顺序执行：

1. 扫描项目目录结构。
2. 识别技术栈。
3. 判断项目类型。
4. 查找已有文档。
5. 查找前端、后端、数据库、测试入口。
6. 识别当前运行方式。
7. 输出项目现状分析。
8. 输出缺失文档列表。
9. 给出接入建议。
10. 用户确认后再补齐文档。

本阶段主要承接 `R1` 和 `R2`：先建立真实现状，再决定补什么文档。

## 3. 项目扫描范围

AI 应优先检查：

- 根目录配置文件
- 包管理文件
- 前端入口
- 后端入口
- 路由定义
- API 定义
- 数据库模型或迁移文件
- 测试目录
- README 或已有文档
- 环境变量示例
- 部署配置

常见文件包括：

```text
package.json
pnpm-lock.yaml
yarn.lock
requirements.txt
pyproject.toml
Cargo.toml
go.mod
pom.xml
build.gradle
Dockerfile
docker-compose.yml
.env.example
README.md
```

## 4. 现状分析输出格式

AI 扫描后必须先输出：

```md
## 已有项目现状分析

### 项目类型

### 技术栈

### 目录结构摘要

### 前端情况

### 后端情况

### 数据库情况

### 测试情况

### 已有文档

### 运行方式

### 发现的风险或不一致
```

## 5. 缺失文档判断

根据项目现状判断是否需要补齐：

| 情况 | 建议文档 |
|---|---|
| 没有总体需求说明 | `docs/requirements.md` |
| 有明显前后端结构 | `docs/architecture.md` |
| 有页面和路由 | `docs/frontend/ui-spec.md` |
| 有 API 路由 | `docs/api/api-spec.md` |
| 有数据库模型或迁移 | `docs/database/data-model.md` |
| 有字段跨层传递 | `docs/contracts/contract-map.md` |
| 没有任务拆解 | `docs/tasks.md` |
| 没有测试说明 | `docs/test-plan.md` |
| 有关键技术选择 | `docs/decision-log.md` |

## 6. 接入建议输出格式

```md
## 接入建议

### 建议补充的文档

### 建议优先级

### 不建议立即修改的部分

### 需要用户确认的问题

### 下一步建议
```

## 7. 补文档规则

用户确认后，AI 可以补齐文档。

补文档时必须遵守：

1. 以当前代码真实情况为准。
2. 不为了文档美观修改代码。
3. 不推断未实现功能为已实现。
4. 不把未来计划写成当前能力。
5. 如果发现代码和用户描述不一致，必须明确标注。

## 8. 接入完成标准

已有项目接入完成应满足：

1. 已明确项目类型。
2. 已生成或更新必要文档。
3. 已说明当前运行方式。
4. 已列出后续任务。
5. 已标注当前风险和缺失项。
6. 未修改无关代码。
7. 后续功能开发可以按 `project-kit/ai-guide/04-feature-development.md` 执行。
